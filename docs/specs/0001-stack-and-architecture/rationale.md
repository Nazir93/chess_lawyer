# 0001. Стек и архитектура: обоснование

## Context

Нужно выбрать стек для закрытой платформы шахматного клуба: Telegram Mini App и PWA из одной кодовой базы, Telegram бот, веб админка, сервер и фоновые задачи. Аудитория 50–100 членов на старте, ориентир до 1 000 и до 200 одновременных сессий (NFR13). Срок 10–12 недель, команда небольшая.

Силы, которые определяют выбор:
- **Производственная планка.** Заказчик ждёт систему, а не прототип: серверный RBAC, атомарная и идемпотентная запись (NFR04), очередь с повторами, staging как production (NFR11), наблюдаемость, восстановление по NFR07, запас по нагрузке.
- **152-ФЗ.** ПДн членов хранятся и обрабатываются в РФ, включая файлы, бэкапы и сбор ошибок. Логи без ПДн.
- **Telegram как источник личности.** Вход по проверенному на сервере initData (Mini App) и Telegram Login (PWA), один аккаунт по `telegram_id`; готовые сервисы аутентификации эту схему не покрывают.
- **Хостинг.** Заказчик выбирает VPS в РФ позже; управляемых облачных сервисов (база, очередь, хранилище секретов) может не быть. Решение должно переноситься между провайдерами.
- **Передача заказчику (NFR09).** Код, миграции, OpenAPI и инструкции передаются; чем меньше языков и сервисов, тем дешевле сопровождение.

Без решения нельзя начать каркас (фича 1), а за ним стоят все срезы.

## Options considered

### Option 1: TypeScript модульный монолит (NestJS, Drizzle, PostgreSQL, Valkey + BullMQ), React клиенты, Docker на VPS

Один язык на всех уровнях, монорепозиторий, сервер NestJS с модулями по областям ТЗ, отдельный процесс `worker` для очереди, PostgreSQL как основная БД, Valkey для очереди и rate limit, развёртывание Docker Compose на двух VPS.

**Pros**:
- Общие схемы Zod для клиента и сервера, OpenAPI из кода.
- NestJS даёт модули, guards и throttler, которые прямо ложатся на RBAC и rate limit.
- Drizzle не прячет SQL, что важно для атомарной записи и блокировок.
- Переносимо на любой VPS.

**Cons**:
- Всю инфраструктуру (БД, Valkey, бэкапы, мониторинг) сопровождаем сами.
- Два хранилища состояния (PostgreSQL и Valkey) вместо одного.

### Option 2: FastAPI (Python) сервер + React клиенты

Сервер на FastAPI с SQLAlchemy и Alembic, очередь на Celery или ARQ, клиенты на React и TypeScript.

**Pros**:
- FastAPI быстрый и даёт OpenAPI из коробки; Pydantic для валидации.
- Сильная экосистема для расчётов (рейтинг).

**Cons**:
- Два языка: схемы клиента и сервера расходятся, нужна генерация типов как отдельный шаг.
- Команде и заказчику сопровождать два набора инструментов, тестов и зависимостей.
- Рейтинг Elo вычислительно тривиален, преимущество Python тут не нужно.

### Option 3: TypeScript монолит с очередью на PostgreSQL (pg-boss), без Redis

Как Option 1, но фоновые задачи в pg-boss внутри PostgreSQL; rate limit тоже в PostgreSQL.

**Pros**:
- Меньше сервисов на VPS, одно хранилище для бэкапа.
- Задача и данные могут ставиться в одной транзакции без outbox.

**Cons**:
- Rate limit и дедупликация webhook на нескольких экземплярах нагружают основную БД частыми записями.
- Лимитер скорости отправки в Telegram и отложенные задачи придётся строить вручную или с меньшими возможностями.

### Option 4: Next.js полный стек (API routes / server actions) на одном приложении

Один Next.js проект для клиента, админки и API, фоновые задачи отдельным процессом.

**Pros**:
- Одна сборка, меньше конфигурации на старте.

**Cons**:
- SEO и серверный рендер не нужны: всё закрыто, Mini App работает как SPA в WebView.
- Границы модулей, RBAC и очередь в Next.js не имеют готового каркаса, всё собирается вручную.
- Админка и клиент в одном приложении усложняют раздельные cookie и CSP.

## Rationale

Option 1 выбран потому, что он прямо закрывает самые дорогие риски из Context: атомарная запись и права держатся в сервере и БД (NestJS guards, Drizzle с явным SQL, ограничения PostgreSQL), а один язык и общие схемы снижают стоимость сопровождения и передачи (NFR09). Инженер выбрал NestJS, Drizzle, BullMQ и два VPS; это совпадает с рекомендацией.

Option 3 честно проще по числу сервисов, но при двух экземплярах `api` нужен общий быстрый счётчик для rate limit и дедупликации webhook, а отправка в Telegram требует лимитера скорости. Valkey даёт это без нагрузки на основную БД; цену (второе хранилище) снимаем transactional outbox, чтобы задача не терялась между БД и очередью.

Хостинг на VPS вместо управляемого облака выбран инженером. Следствие: бэкапы через WAL-G в S3 хранилище в РФ, секреты через SOPS. GlitchTip стоит на production VPS, а не на staging: иначе данные production попадали бы на staging вопреки ТЗ §12. На staging остаётся только Uptime Kuma, который видит production снаружи и данных не получает. Production на одном VPS переживает отказ процесса (по два экземпляра `api` и `worker`), но не отказ сервера; с NFR01 это может не сойтись, поэтому вопрос вынесен заказчику (Q31). Путь к третьему VPS открыт, так как сервер не хранит состояние в процессе.

## Пересмотр после независимой проверки

Проверка другой моделью нашла ошибки, исправленные в `index.md`: один `worker` нарушал NFR12; выкат без простоя не был обеспечен (добавлены фиксированные экземпляры, активная проверка здоровья и сценарий выката); webhook мог потерять обновление при недоступном Valkey (теперь сначала запись в PostgreSQL); GlitchTip на staging переносил данные production; доставка «ровно один раз» была завышенной гарантией. Установленные скиллы `nestjs/agent-skills` описывают первые пакеты NestJS 12 для сессий, прав, outbox и проверок здоровья; по правилу скиллов они заменили самописные решения. Адаптер сменён с Fastify на `@nestjs/platform-node`: он быстрее Express и совместим с сессиями и CSRF защитой этих пакетов. `@nestjs/observe` не используется: он отправляет телеметрию во внешний сервис.
