## 1. Цели и границы проекта

Создать качественную закрытую цифровую среду для представителей юридического сообщества Москвы. Приоритеты: вступление по приглашению, управление статусами членов, календарь мероприятий, регистрация на турниры, внутренний шахматный рейтинг и удобное администрирование.

**Критерий успеха MVP:** член клуба самостоятельно входит через Telegram (в Mini App или в PWA), видит персональную карту, записывается на мероприятие и получает уведомления; администратор одобряет заявки и публикует результаты без помощи разработчика.

**Измеримые цели пилота** _(предложение)_: не менее 80% одобренных членов вошли хотя бы раз за первый месяц; запись на мероприятие занимает не больше 3 нажатий с главной; администратор рассматривает заявку не дольше 5 минут; ноль инцидентов с утечкой ПДн.

## 2. Клиенты и каналы

| Клиент | Для кого | Вход | Уведомления |
|---|---|---|---|
| **Telegram Mini App** | Члены, кандидаты, посетители, организаторы | Подписанный initData Telegram | Бот |
| **PWA** (устанавливаемое веб приложение) | Те же члены и организаторы вне Telegram, на телефоне и компьютере | Официальный Telegram Login, тот же аккаунт по `telegram_id` | Бот (основной) + Web Push (по согласию) |
| **Telegram бот** | Все | | Основной канал уведомлений |
| **Веб панель администратора** | Администраторы, суперадминистраторы, организаторы | Отдельный вход с обязательной 2FA | |

Правила:
- Mini App и PWA собираются из **одной кодовой базы** и показывают одинаковые экраны S01–S17. Отличается только слой платформы: вход, системные кнопки, тема, уведомления, установка.
- Один человек = один `telegram_id` = один аккаунт, в какой бы клиент он ни вошёл. Членство, записи, рейтинг общие.
- Подача заявки и активация приглашения доступны в обоих клиентах.
- PWA не является публичным сайтом: до входа видна только закрытая приветственная страница, без каталога, мероприятий и мест проведения. Поисковая индексация запрещена (`noindex`).
- Админка остаётся отдельным веб приложением и в PWA не входит.

## 3. Персоны, роли и доступы

### 3.1 Роли

| Роль | Права |
|---|---|
| Посетитель | Просмотр закрытой приветственной страницы, активация приглашения |
| Кандидат | Подача и изменение заявки до решения, статус рассмотрения, уведомления |
| Действительный член | Профиль, карта, календарь, запись, рейтинг, каталог (при согласии) |
| Организатор | Мероприятия, явка, результаты, но только на назначенных ему мероприятиях; без доступа к лишним ПДн |
| Администратор | Заявки, членство, приглашения, мероприятия, турнирные данные, контент |
| Суперадминистратор | Роли администраторов, системные настройки, выгрузки, аудит |

Почётное членство: отображаемый статус поверх роли, прав не меняет. Организатор назначается на конкретное мероприятие (Q11), сам он обычно член клуба.

### 3.3 Жизненные циклы статусов

- **Заявка:** `draft` → `submitted` → (`needs_info` ⇄ `submitted`) → `approved` | `rejected`. Кандидат может отозвать заявку до решения (`withdrawn`). Решение окончательное; исправление только новой заявкой.
- **Членство:** `active` → `suspended` ⇄ `active`; `active` | `suspended` → `terminated` (окончательно). Членский номер не переиспользуется (Q13).
- **Приглашение:** `active` → `exhausted` (лимит) | `expired` (срок) | `revoked` (отозвано).
- **Регистрация:** `registered` → `cancelled` | `attended` | `no_show`; `waitlisted` → `offered` → `registered` | `offer_expired` | `cancelled`.
- **Мероприятие:** `draft` → `published` → `registration_closed` → `completed`; из `draft` и `published` возможно `cancelled`.
- **Турнир / результаты:** `draft` → `submitted` (организатор) → `published` (администратор) → `corrected` (новая версия с пересчётом).

Любой переход, кроме переходов внутри черновика, пишется в аудит с исполнителем и основанием.

## 4. Бизнес правила

| Код | Правило | Значение по умолчанию |
|---|---|---|
| BR01 | Срок действия приглашения | 14 дней _(предложение)_ |
| BR02 | Лимит использований приглашения | 1 (именное) или до N (групповое), Q12 |
| BR03 | Перебор кодов приглашения | не больше 5 неудачных попыток в час с одного аккаунта и IP, затем пауза |
| BR04 | Свежесть initData и данных Telegram Login | не старше 24 часов при входе _(предложение)_; повтор одних и тех же данных отклоняется |
| BR05 | Сессия члена | 30 дней скользящая, отзывается при приостановке членства и выходе |
| BR06 | Сессия администратора | 8 часов, 2FA при каждом входе, выход после 30 минут бездействия _(предложение)_ |
| BR07 | QR членской карты | подписанный токен, живёт 60 секунд, обновляется автоматически, одноразовый для отметки явки |
| BR08 | Дедлайн записи и отмены | задаётся на мероприятии; по умолчанию за 24 часа до начала _(предложение)_ |
| BR09 | Лист ожидания | порядок по времени постановки в очередь (Q05); место предлагается одному человеку |
| BR10 | Срок подтверждения предложенного места | 12 часов, но не позже дедлайна записи _(предложение)_ |
| BR11 | Неявка | фиксируется организатором; ограничения за неявки в MVP не применяются |
| BR12 | Рейтинг | LCC Rating по утверждённой формуле (Q04); пересчёт только после публикации администратором |
| BR13 | Членский номер | формат `LCC-0001`, выдаётся по порядку, не переиспользуется _(предложение, Q13)_ |
| BR14 | Удаление данных | по запросу члена через администратора в течение 30 дней, с сохранением обезличенных рейтинговых записей _(предложение, Q16)_ |

## 7. Ключевые сценарии и критерии приёмки

- **UC01 Вступление.** Администратор создаёт приглашение → кандидат открывает его в Mini App или PWA → вход через Telegram → заявка → проверка → одобрение → членский номер → закрытый доступ и уведомление.
  **AC:** истёкшее, отозванное и исчерпанное приглашение не активируется; две одновременные активации последнего использования не проходят обе; без одобрения закрытые экраны недоступны даже по прямой ссылке на API.
- **UC02 Запись.** Член открывает мероприятие → сервер проверяет членство, дедлайн и места → регистрация атомарно фиксируется → бот подтверждает → при заполнении включается лист ожидания.
  **AC:** 50 одновременных запросов на последнее место дают ровно одну регистрацию; двойной клик не создаёт вторую запись; после дедлайна запись закрыта.
- **UC03 Отмена и лист ожидания.** Участник отменяет запись → место предлагается первому в очереди → бот (и Web Push, если включён) присылает предложение с дедлайном → без подтверждения место уходит следующему.
  **AC:** место никогда не предлагается двум людям сразу; просроченное предложение переходит дальше автоматически.
- **UC04 Публикация результатов.** Организатор вносит или импортирует итоги → проверка полноты и допустимости → администратор подтверждает → пересчёт рейтинга и протокол.
  **AC:** проверочные примеры расчёта рейтинга совпадают с ожидаемыми до последнего знака; исправление результата пересчитывает рейтинги всех затронутых игроков, история сохраняется.
- **UC05 Блокировка.** Администратор приостанавливает членство → сервер сразу отказывает в закрытых ресурсах во всех клиентах → активные сессии отзываются → доступ к закрытому чату синхронизируется в пределах прав бота → действие в аудите.
  **AC:** следующий запрос с любого устройства после приостановки получает отказ; QR карты перестаёт проходить проверку.
- **UC06 Вход в PWA** (новое). Член открывает PWA → «Войти через Telegram» → сервер проверяет подпись данных Telegram → находит аккаунт по `telegram_id` → выдаёт сессию → предлагает установку и уведомления.
  **AC:** поддельная или устаревшая подпись отклоняется; пользователь видит те же записи и карту, что в Mini App; выход завершает сессию и очищает локальные данные.
- **UC07 Проверка на входе** (новое). Организатор открывает S17 → сканирует QR члена → сервер проверяет токен, членство и запись → отметка явки.
  **AC:** просроченный или уже использованный QR не проходит; организатор чужого мероприятия не может отметить явку.

## 9. Шахматная модель и рейтинги

- В MVP нет онлайн партий, шахматного движка, античита и автоматической швейцарской жеребьёвки.
- У каждого турнира: формат, контроль времени, число туров, регламент, участники, результаты и отметка «рейтинговый / нерейтинговый».
- Внутренний **LCC Rating** по зафиксированному регламенту. Предложение для утверждения (Q04): Elo, стартовый рейтинг 1500, K = 40 первые 20 партий, затем K = 20; результат партии 1 / ½ / 0; неявка или техническое поражение в рейтинг не идёт. Формула утверждается ДО реализации, к ней прилагаются не меньше 5 проверочных примеров с ожидаемыми значениями.
- Не использовать название «официальный рейтинг ФШР/FIDE». Внешние рейтинги: необязательное поле со ссылкой на источник, без синхронизации.
- Результат не редактируется бесследно: коррекция создаёт новую версию и пересчёт от точки изменения.
- Ввод результатов: вручную по турам и импорт файла (Q15); перед публикацией экран сверки с ошибками.
- **Системы турнира в MVP** _(предложение, Q29)_: швейцарская (пары вносит организатор или импорт, автоматической жеребьёвки нет), круговая, свободная встреча (партии без туров). Система влияет на проверку результатов и тай-брейки (например Бухгольц, личная встреча). Арена, 960, bughouse, олимпийская и командные системы вне MVP.
- **Свободные партии** после турнира можно записать для истории; в LCC Rating они идут, только если мероприятие помечено рейтинговым и это разрешено регламентом (Q04).
- **Отображение результатов:** итоговая таблица — место, имя, рейтинг, очки, запись `+победы =ничьи −поражения`; в профиле — W/D/L и изменение рейтинга по каждой партии.
- **Новички:** пока у члена меньше N рейтинговых партий, рейтинг помечается как предварительный (провизорный); правило отображения решает Q04.

## 11. Требования к PWA

- Манифест: название, иконки (включая maskable), цвет темы Emerald, `display: standalone`, стартовый адрес.
- Устанавливается на Android (Chrome), iOS (Safari, «На экран Домой»), desktop (Chrome, Edge, Safari).
- Service worker кэширует только оболочку приложения и статические файлы. **Ответы закрытого API и ПДн не кэшируются** и не пишутся в локальное хранилище устройства.
- Сессия в cookie `HttpOnly`, `Secure`, `SameSite=Lax` или строже; токены не хранятся в `localStorage`.
- Выход и приостановка членства очищают кэши и подписку Web Push на устройстве.
- Обновление версии: при выходе новой версии пользователь видит «Доступно обновление»; старая оболочка не работает с несовместимым API.
- Web Push по стандарту VAPID; на iOS работает с iOS 16.4 и только у установленного приложения; без разрешения всё работает через бота.
- Домен PWA подтверждается у бота в BotFather для Telegram Login.
- Заголовки безопасности: CSP, HSTS, `X-Content-Type-Options`, запрет встраивания во фреймы (кроме того, что требует Telegram для Mini App).

## 12. Техническая архитектура

Проект сдают как **производственную систему**, а не как прототип: продуманная архитектура, защита на сервере, наблюдаемость и запас по нагрузке заложены с первой спеки, а не «добавим потом».

**Принципы архитектуры**
- Чёткие границы модулей (доступ, членство, мероприятия, турниры/рейтинг, уведомления, админка); зависимости направлены внутрь к домену, а не наоборот.
- Один источник правды для правил (статусы, RBAC, запись, рейтинг) на сервере; клиент только отображает.
- Конфигурация и секреты вне кода; окружения: local, staging, production с одинаковым способом развёртывания.
- Фоновые задачи (напоминания, лист ожидания, push, пересчёт) через очередь с повторами и идемпотентностью.
- Горизонтальный запас: API и воркеры масштабируются добавлением инстансов; состояние сессий и очередей не привязано к одному процессу.
- Наблюдаемость с первого дня: структурированные логи без ПДн, метрики (latency, ошибки, очередь), алерты по недоступности и ошибкам 5xx.
- Безопасность по умолчанию: TLS, RBAC на каждой закрытой операции, rate limit, аудит критических действий, минимум ПДн, проверка OWASP ASVS L2 перед сдачей.
- Нагрузка заложена в архитектуру: целевой ориентир NFR02 плюс запас до ~1 000 членов и пиковых записей на популярное мероприятие; конкурентная запись проверяется тестом с первого среза мероприятий.

- **Клиент:** React + TypeScript; одна кодовая база для Mini App и PWA, слой платформы изолирован (вход, тема, кнопки, уведомления). HTTPS.
- **Сервер:** Node.js (NestJS) или Python (FastAPI), фиксируется в архитектурной спеке (Q08); REST API с версионированием `/v1`; авторизация и права только на сервере.
- **Хранилище:** PostgreSQL на инфраструктуре в РФ (Q17); миграции, ежедневные резервные копии.
- **Telegram бот:** `/start`, `/help`, Menu Button «Открыть приложение», заполненные описание и карточка «Что умеет этот бот?» (закрытый клуб, вход по приглашению); ответ на `/start` зависит от статуса: посетитель — как получить приглашение, кандидат — статус заявки, член — ближайшее мероприятие и кнопка приложения; уведомления; webhook с секретным заголовком и дедупликацией.
- **Файлы и медиа:** аватары и фото площадок хранятся в объектном хранилище в РФ, отдаются по подписанным ссылкам только авторизованным пользователям; при загрузке сжимаются и очищаются от метаданных (EXIF с геопозицией).
- **Фоновые задачи:** очередь для уведомлений, напоминаний, истечения предложений мест и пересчёта рейтинга; повтор с ограничением; идемпотентность.
- **Админка:** отдельный домен или маршрут, серверный RBAC и 2FA.
- **Окружения:** локальное, тестовый стенд, продакшен; данные продакшена на стенд не копируются.
- **Наблюдаемость:** структурные логи без ПДн и секретов, сбор ошибок клиента и сервера, проверка доступности.

## 15. Безопасность и правовая подготовка

- initData (Mini App) и данные Telegram Login (PWA) проверяются только на сервере по официальной процедуре; `initDataUnsafe` не доказательство личности; проверяется свежесть (BR04), повтор отклоняется.
- Каждая закрытая операция проверяется сервером по матрице 3.2; прямой доступ к чужим профилям, картам, заявкам запрещён (проверка владельца на каждом идентификаторе).
- Токен бота, ключи VAPID, ключ подписи QR только в серверной конфигурации, ротация описана.
- Минимизация ПДн: не собирать паспорта, удостоверения и документы о статусе; проверка профессии по утверждённому процессу.
- До старта обработки: оператор ПДн, цели, правовые основания, политика, согласия, договоры с подрядчиками, уведомление Роскомнадзора, оценка трансграничной передачи (Telegram, push сервисы Apple и Google).
- Учесть ч. 5 ст. 18, ст. 18.1, ст. 22 Закона № 152-ФЗ; размещение БД в РФ не снимает вопросов о передаче через Telegram и push сервисы.
- TLS, ежедневные копии, проверка восстановления, минимальные права администраторов, журнал критических действий, ограничение частоты, защита от перебора.
- QR карты: подписанный краткосрочный токен без ПДн, проверка только на сервере (BR07).
- PWA: см. раздел 11 (не кэшировать закрытые данные, cookie `HttpOnly`, CSP, очистка при выходе).
- Фото члена клуба — его персональные данные: загружаются только по его действию, видны только членам клуба, удаляются при удалении профиля; фото площадок ПДн не содержат.
- Списки записавшихся и неявок другим членам показываются только в объёме, утверждённом в Q27 и Q28.
- Тестовые и демонстрационные данные только вымышленные. Скриншоты референса содержат имена и фото реальных людей: не публикуются, не используются в макетах и тестовых данных, хранятся только в закрытом репозитории.
- Перед сдачей: проверка по OWASP ASVS уровня 2 для API и админки _(предложение)_.

| NFR03 | Первое открытие экрана до 3 с на 4G; повторное открытие PWA до 1,5 с за счёт кэша оболочки |
| NFR04 | Двойная регистрация невозможна, вместимость не превышается при параллельных запросах |
| NFR05 | Поддержка: Telegram iOS, Android, Desktop актуальных версий; браузеры для PWA: Safari iOS 16.4+, Chrome Android, Chrome, Edge, Safari, Firefox последних двух версий на компьютере |
| NFR06 | PWA проходит проверку устанавливаемости Lighthouse; доступность Lighthouse не ниже 90 |
| NFR07 | Восстановление из резервной копии не дольше 4 часов, потеря данных не больше 24 часов |
| NFR08 | Логи без ПДн и секретов; хранение логов 90 дней _(предложение)_ |
| NFR09 | Поддерживаемость: код, инструкции, миграции, схема БД, OpenAPI, шаблон конфигурации и доступы передаются заказчику |
| NFR10 | Архитектура модульная с явными границами; новый срез не ломает уже работающие без миграции и без «временных» обходов прав |
| NFR11 | Staging повторяет production по схеме развёртывания; перед релизом проходят автотесты, проверка безопасности из раздела 17 и смоук основных UC |
| NFR12 | При отказе одного инстанса API или воркера система продолжает принимать запросы на оставшихся; деградация уведомлений не блокирует запись и вход |
| NFR13 | Целевой запас по нагрузке: до 1 000 членов, до 200 одновременных сессий на стенде без деградации выше NFR02; пик записи на одно мероприятие (параллельные POST register) не превышает вместимость |
| NFR14 | Секреты только в секрет-хранилище окружения; ротация токена бота и ключей сессий описана; доступ к production только по принципу минимальных прав |

## 17. Тестирование и приёмка

- Автотесты: правила доступа по матрице 3.2, все переходы статусов 3.3, бизнес правила BR01–BR14, расчёт рейтинга на проверочных примерах, конкурентная запись (UC02), лист ожидания (UC03), проверка подписи Telegram (обе схемы входа).
- Ручная проверка по чек листу на Telegram iOS, Android, Desktop и на установленной PWA iOS и Android; особенности платформ документируются.
- Нагрузочный тест NFR02 и NFR13 и тест конкурентной записи на стенде; сценарий пиковой записи на популярное мероприятие.
- Проверка безопасности: чужие идентификаторы в запросах, истёкшие сессии, приостановленный член, перебор кодов, кэш PWA после выхода, rate limit, отсутствие секретов в клиенте и логах, проверка OWASP ASVS L2 для API и админки.
- Приёмка: тестовый стенд, чек листы, перечень дефектов; критические и высокие дефекты закрываются до подписания акта.

## 19. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Не закрыты Q01, Q04, Q05 к неделе 1 | Сдвиг сроков, переделка | Решения фиксируются до старта соответствующих фич, иначе фича ждёт |
| Ограничения Web Push на iOS | Часть членов без push | Бот остаётся основным каналом |
| Блокировки или сбои Telegram в РФ | Нет входа и уведомлений | Мониторинг; резервный вход вне Telegram вынесен в этап 2 |
| Передача ПДн через Telegram и push сервисы | Правовой риск | Минимум ПДн в сообщениях, оценка трансграничной передачи до запуска |
| Дизайн позже недели 2 | Сдвиг фронтенда | Дизайн система по разделу 10 и референсам, макеты донастраиваются |
| Ошибка в формуле рейтинга после старта | Недоверие членов | Проверочные примеры, версия формулы в протоколе, пересчёт |

## 20. Вне MVP и план развития

- Онлайн партии, собственный шахматный сервер, античит, трансляции, движки.
- Автоматическая швейцарская жеребьёвка, официальная сертификация.
- Платное членство, автоплатежи, бухгалтерия, юридически значимый документооборот.
- Нативные приложения в магазинах, публичный сайт, CRM, внешние шахматные площадки.
- Автоматическая проверка адвокатского статуса по реестрам.
- Вход без Telegram (телефон, email).
- **Этап 2:** онлайн запись на циклы, платежи после правовой оценки, расширенные графики рейтинга, экспорт протоколов, партнёрские приглашения, интеграция с турнирным ПО, английский язык.
